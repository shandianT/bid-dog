# 分段生成与检查点续跑设计

## 背景

当前默认链路把“读取招标文件、提取评分与废标项、规划目录、撰写全部章节、汇总、出 Word、质检”交给一条 OpenCode 长会话。任务目录虽然会持续落盘，但调度边界仍是整单：长连接静默后先等待，再向同一会话发送续做提示，仍失败时可能切到 CLI 兼容路径。最近实测中，本地招标解析约 4 分钟完成，后续模型静默、8 分钟停滞门限、续做与第二条连接累计把总时长拖到 30～40 分钟。

## 目标

将新任务改为由中标狗引擎主导的短节点流水线，使模型或网络中断最多影响当前节点，已完成解析、规划和章节不重复执行；默认使用极速模型，标准模型仅用于用户明确选择的关键复核。常规标书的产品目标是 12～20 分钟完成，并在任一时刻向用户展示当前节点、已用时间、通常耗时和重试次数。

该目标是工程预算，不是上游模型 SLA。上游服务完全不可用时任务仍会停止，但必须停在可继续的节点检查点，而不是从头重跑。

## 方案比较

### 方案 A：继续使用单一长会话，只缩短超时

改动最小，但长上下文、重复读文件和整单续做问题仍然存在。缩短超时只会更快触发重试，不能减少重做范围，容易形成重试风暴，不采用。

### 方案 B：引擎主导的分段流水线（采用）

本地确定性完成文件解析和 Word/质检；模型工作拆成响应规划和独立章节节点。每个节点有输入摘要、输出文件、模型档位、状态、尝试次数和检查点。断流只重试当前节点，完成节点不重放。该方案保留 OpenCode 的工具能力，同时把失败域限制在几分钟内。

### 方案 C：完全绕过 OpenCode，全部直接调用模型 API

短请求更快，但会一次性重写现有工具、素材读取、文件编辑和用户插话协议，迁移风险高，也无法复用已验证的 OpenCode 服务模式。本期不采用；后续可把纯结构化提取节点逐步下沉为直接 API。

## 总体架构

新任务由 `GenerationPipeline` 驱动，任务目录仍是唯一事实来源，不引入数据库。流水线包含六类节点：

1. `source_parse`：本地读取 DOCX、PDF、TXT，生成 `招标文件_解析版.md` 与解析清单。
2. `response_plan`：极速模型基于解析文本和模板生成投标文件组成、评分点矩阵、废标风险和章节任务清单。
3. `chapter_write:<id>`：极速模型按章节独立生成正文或偏离表；最多两个节点并发，避免网关限流。
4. `assemble`：本地确定性汇总章节，生成可审阅 Markdown。
5. `quality_review`：极速模式只跑确定性质检；标准模式才调用标准模型复核关键章节，输出修改建议，不直接伪造事实。
6. `word_export`：本地脚本生成 Word、运行格式门禁并核验最终产物。

OpenCode 仍是模型节点的默认执行外壳，但不再拥有整单调度权。每个模型节点使用独立的短会话或独立轮次，只能读取该节点声明的输入文件，并只写声明的输出文件。

## 持久化合同

每个任务新增 `pipeline.json`，使用现有原子 JSON 写入机制保存：

```json
{
  "version": 1,
  "run_id": "本轮标识",
  "mode": "fast",
  "state": "running",
  "current_nodes": ["chapter_write:03"],
  "nodes": [
    {
      "id": "chapter_write:03",
      "kind": "model",
      "state": "running",
      "model_tier": "fast",
      "input_digest": "sha256",
      "outputs": ["03_总体架构与技术路线.md"],
      "attempt": 1,
      "started_at": "2026-08-21 16:00:00",
      "last_activity_at": "2026-08-21 16:01:12",
      "error_code": ""
    }
  ]
}
```

节点状态只有 `pending`、`running`、`done`、`retry_wait`、`failed`、`blocked`、`skipped`。`done` 必须同时满足：进程或会话正常收尾、声明输出存在、输出通过该节点的最低验证。仅收到模型“完成”文本不能置为 `done`。

节点幂等键为 `run_id + node_id + input_digest`。同一键已完成时直接复用；输入摘要变化时创建新尝试，但旧输出先归档，不原地覆盖。`pipeline.json` 不保存原始凭据、完整模型响应或客户正文。

现有 `progress.json`、`events.jsonl` 和 `flow` 合同继续保留，由流水线节点确定性映射到已有 12 步和六段流程台。旧任务没有 `pipeline.json` 时继续走现有单会话恢复逻辑，避免升级后无法续做。

## 本地解析

任务创建时已保存的主件是唯一解析输入。DOCX、PDF、TXT 分别由本地库提取正文、标题和表格；解析结果写入 `招标文件_解析版.md`，并在 `source_manifest.json` 记录文件摘要、页数或段落数、表格数、字符数和警告。

解析设置资源和复杂度上限：文件大小沿用上传门限；DOCX 检查 ZIP 条目数、解压总量和压缩比；PDF 限制页数、单页字符数和总字符预算。无法提取足够正文时节点进入 `blocked`，明确要求用户换可检索文件或手动确认，不把空解析交给模型继续猜测。

模板推荐与正文解析共享本次已提取文本，不再次读取主件。表格内容只进入本轮解析文件和模型输入，不进入模板持久化元数据。

## 模型路由

默认模式为 `fast`：响应规划和章节撰写使用 `deepseek-v4-flash`，最终质量阶段只跑确定性检查。`standard` 模式仍先用极速模型处理解析、规划和一般章节，仅对标记为关键的章节及最终复核使用 `senseaudio-s2`。

每个任务在创建时冻结 `model_routes`，包含模型名、网关、协议、TLS 策略和不可逆凭据指纹。任务运行中修改全局设置不影响本轮；续跑若凭据或网关已经改变，只重建尚未完成节点的新会话，不复用不兼容的旧会话。

同一网关模型并发上限默认为 2。收到 429 或网关过载信号时自动降为 1，不并发重试。模型不存在、未授权或套餐不支持属于永久错误，直接阻断节点并提示切换模型，不消耗重试次数。

## 超时、重试与恢复

活动信号包括 OpenCode SSE、模型输出增量、受控工具事件和节点输出文件变化。只有真实活动才刷新 `last_activity_at`；UI 轮询和内部心跳不能伪装进度。

短节点使用两级门限：达到慢响应门限时只提示，不重启；达到停滞门限后中断当前节点并最多重试两次。退避期间写入 `retry_wait` 和下一次时间。重试提示词只包含该节点的输入清单、既有临时输出摘要和缺失验收项，不重放整单提示词。

节点先写带尝试标识的临时文件，通过校验后再原子提升为正式输出。中断时保留临时文件作为诊断证据，但后续节点只读取正式输出。应用退出或系统重启后，启动恢复器把遗留 `running` 节点标为可恢复并重新执行当前节点；所有 `done` 节点保持不动。

不再自动切换到整单 CLI 兼容模式。OpenCode 服务无法工作时，新流水线停在当前节点并提供“重试当前节点”“从检查点继续”“查看诊断”；SoWork 只在用户显式选择时走旧兼容路径。

## 章节任务与汇总

`response_plan` 必须输出结构化章节清单，每章包含唯一 ID、标题、招标依据、评分点、素材槽位、目标文件和前置依赖。引擎验证清单后才派发章节节点。章节节点不得自行改变目录、创建未声明子任务或出最终 Word。

章节完成后先检查非空、标题层级、最低信息量、禁止编造标记以及要求的表格列。两章不得写入同一目标文件。汇总阶段按冻结目录顺序读取正式章节输出，确定性生成整册；缺章时拒绝汇总并回到对应节点，不让模型凭记忆补齐。

## UI 与用户反馈

现有六段流程台继续使用，但当前阶段展开到节点级：

- 当前动作，例如“正在撰写第 3/8 章：总体架构与技术路线”。
- 当前节点已用时间、历史通常耗时和剩余区间。
- 并行状态，例如“2 个章节生成中，4 个已完成，2 个等待”。
- 网络状态，例如“第 1 次重连，18 秒后重试当前章节”。
- 最近检查点，例如“已完成：响应规划；已保存 4/8 章”。

“稳定模式”文案退出新流水线。用户看到的是具体行为：“当前章节连接中断，正在第 1/2 次重试；其他已完成章节不会重写”。前端刷新、SSE 断开或切到后台只影响连接徽标，不改变节点事实，也不会触发生成。

阶段耗时来自同类节点的历史统计，首次运行展示区间而不是虚假精确倒计时。超过历史 P90 时标记“已超出通常耗时”，但只由后端停滞判定决定是否重试。

## 接口

- `GET /v1/jobs` 的 `flow` 增加 `node_summary`、`current_nodes`、`retry` 和阶段耗时区间；旧字段保持兼容。
- `GET /v1/jobs/{id}/pipeline` 返回脱敏节点状态，用于诊断和 UI 详情。
- `POST /v1/jobs/{id}/resume` 对新任务恢复未完成节点；旧任务继续恢复原 OpenCode 会话。
- `POST /v1/jobs/{id}/nodes/{node_id}/retry` 只重试失败或阻断的当前节点，并使用幂等请求键防双击。
- 停止任务会中断所有运行节点，保留完成节点和临时证据；再次继续不重做完成节点。

## 安全与资源边界

- 本地解析不执行文档宏、外链或嵌入程序。
- 模型节点只获得任务目录中声明的只读输入和单一目标输出，不获得全盘目录。
- 日志、事件、`pipeline.json` 和诊断包继续统一脱敏，不记录 Key。
- 并发工作线程沿用全局任务准入和 owner 生命周期，单个任务内部最多两个模型节点；停止、删除和关闭应用必须回收全部子进程与会话。
- Word 汇总和确定性质检零模型额度，失败可独立重试。

## 兼容与迁移

- 仅新建或明确重跑的任务使用流水线 v1。
- 已有 `oc_session` 且没有 `pipeline.json` 的任务保持原恢复方式。
- 已有章节但未完成的旧任务可由“按当前模式新建续跑版本”扫描正式产物并建立已完成节点；原任务目录不修改。
- `mock`、SoWork、Claude、Codex 和自定义命令暂时保留旧整单路径；默认 `s2/opencode` 才启用新流水线。

## 交付分期

第一期完成默认 OpenCode 链路：本地解析、响应规划、章节节点、检查点、极速模型路由、确定性汇总/Word、节点级 UI 与恢复。标准模型的关键章节复核保留接口和路由合同，但不在第一期自动修改正文，先作为可审阅报告输出。

第二期再根据真实标书 A/B 数据决定是否增加直接 API 结构化提取、动态并发和标准模型自动修订，避免在没有质量证据时扩大自动化范围。

## 验收标准

1. DOCX、PDF、TXT 主件无需模型即可生成非空解析文件和来源清单；危险或空文件明确阻断。
2. 同一主件在模板推荐和任务运行中只执行一次正文提取。
3. 默认新任务冻结极速模型；标准模式只把关键复核节点路由到标准模型。
4. 任一章节在生成中断后只重试该章节，已完成解析、规划和其他章节的摘要与修改时间保持不变。
5. 应用退出后重启能从 `pipeline.json` 恢复未完成节点，不依赖旧 OpenCode 会话仍存在。
6. 双击继续或节点重试只产生一次执行；停止能回收所有并行节点。
7. 缺章、空章或缺必要表格时不能进入汇总；最终 Word 和格式报告均存在且有效才标记任务完成。
8. UI 正确显示当前章节、完成数量、重试次数、真实已用时间和历史耗时区间，不再把后续撰写显示成“招标解析”。
9. 旧任务、旧 CLI 生成方式和已有诊断包接口保持可读、可恢复或给出明确兼容提示。
10. Python、前端静态、Playwright、Rust、真实 OpenCode 契约及 macOS/Windows 安装载荷测试全部通过后才发布。
