# Windows 生成链路恢复设计

## 背景与目标

客户在 Windows 首次生成时遇到四类相互关联的问题：自动模板创建阶段长时间无反馈、生成进程停在第 1 步、诊断按钮没有可感知响应、正文存在但 Word 导出失败。目标是让桌面安装版在没有 Python、Node、Codex、SoWork 的新机器上也能启动默认生成链路；缺少或损坏的组件必须被明确识别、自动修复或给出可执行的恢复动作。

## 已确认根因

1. PyInstaller 只安装了 `python-docx`，没有收集 `docx/templates/*.xml` 等数据文件，导致成品引擎运行 `Document()` 时找不到 `default-header.xml`。
2. 自动模板在前端调用 `/v1/templates/recommend` 后，建任务时 `/v1/jobs` 又读取并解析同一主件；手选模板会绕开这两次同步解析，因此只有自动模式表现为卡顿。
3. 任务在真正建立生成连接前就统一显示“已派发，正在读招标文件”，组件检查、外壳启动、会话建立、模型探活都挤在第 1 步里。
4. Tauri 壳层找不到或无法启动 `bid-engine` 时只返回 `None`，前端最终进入演示模式，用户无法区分端口等待、安装损坏、杀毒软件隔离和引擎异常退出。
5. 诊断弹窗层级低于错误卡片，且诊断按钮没有同步切换为运行态；后端离线时也没有壳层启动证据可展示。
6. 默认 S2 链路已经以 OpenCode 为执行外壳，但兼容入口仍允许旧配置把 `senseaudio-s2` 交给 Codex ChatGPT 登录态，产生“不支持该模型”的误导错误。

## 方案

### 1. 单一启动预检

后端提供一个快速、无外网副作用的生成预检结果，统一描述数据目录、技能包、模板、执行外壳、模型凭证和当前运行路径。每次任务启动先发出确定性的预检工作台词，再进入 OpenCode 会话；无法继续时在进入 12 阶段正文流程前终止，并给出自动修复动作。

默认 S2/OpenCode 外壳缺失时，后端启动已存在的固定版本下载器。下载进度复用 `/v1/agent/provision`，任务界面显示“正在修复生成组件”，修复成功后继续当前任务，失败则保留任务为可重试状态。SoWork 仅在用户显式选择时参与检查。

### 2. 自动模板单次解析

`auto`、`default` 和空模板值统一归一化为自动推荐。前端预览推荐只用于展示，不再阻塞创建任务；后端以任务创建请求为唯一决策点，只读取和解析主件一次，冻结 `template_recommendation` 与 `template_snapshot`。解析失败时回退综合政府模板并明确记录低置信度，而不是返回不存在的 `default` 模板错误。

### 3. 可感知的启动和诊断

任务启动依次展示：保存文件、识别模板、检查生成组件、建立模型连接、读取招标文件。第 1 个业务阶段仍是读取招标文件，但其前置状态使用 `step=0`，不再伪装成已经进入第 1 步。

诊断按钮点击后同步打开诊断面板、切换按钮文案并隐藏遮挡错误卡片。诊断接口返回当前任务最近阶段、最后活动时间、外壳路径来源和自愈状态；本地引擎无响应时，前端明确提示“本地引擎未启动”，而不是无动作。

### 4. 安装包完整性门禁

PyInstaller 显式收集 `docx` 数据。Windows 和 macOS 安装包烟测不只验证 `/v1/health`，还在最终安装载荷中的 `bid-engine` 上调用确定性 Word 导出路径，确认生成非空 `.docx`。Windows 壳层记录引擎候选路径、spawn 错误和健康等待状态；sidecar 缺失或启动失败时不静默进入演示模式。

源代码一键启动脚本继续做 Python 依赖探测和按需安装，但桌面客户交付以包含 `bid-engine + opencode-cli` 的安装包为准，不要求客户安装 Python、Node 或 SoWork。

### 5. 安全与兼容边界

- 不读取或覆盖客户现有 `~/.codex` 登录态。
- `senseaudio-s2` 只经 S2/OpenCode 自定义 provider 路径运行；显式 Codex 模式只能选择其账号支持的 OpenAI 模型。
- 自动修复只写应用数据目录，并校验固定版本二进制的 `--version`；不写系统目录，不请求管理员权限。
- 已生成内容和原任务目录始终保留；重试创建子轮次或续跑，不覆盖交付历史。

## 验收标准

1. `template_id` 为 `auto`、`default` 或空值时都能创建任务，并冻结一个存在的场景模板快照。
2. 自动模板创建不再等待前端推荐请求，也不会对同一文件做两次同步解析。
3. 点击“一键诊断”立即出现面板和运行状态；后端在线、离线两种路径均有可读结果。
4. 缺少 OpenCode 时任务显示修复进度，修复成功可继续；默认路径不检查 SoWork。
5. Windows 壳层的引擎缺失、spawn 失败、健康超时均能被区分并落日志。
6. 最终安装载荷中的 `bid-engine` 可以从 Markdown 生成非空 Word，不再缺少 `default-header.xml`。
7. 现有后端、前端、浏览器和 Rust 测试通过；安装包级测试在 CI 中成为发布阻断门禁。
