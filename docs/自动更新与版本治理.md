# 自动更新与版本治理

回答一个商业化前提问题:**"版本怎么由我们把控?收费后用户拿旧版一直白嫖怎么办?"**

## 总体设计(三层)

```
┌ 1. 自动更新通道(Tauri updater)────────────────┐
│ 应用内检查签名清单 → 下载校验 → 安装 → 自动重启 │  能力:把新版"推"到用户手里
├ 2. 发布策略文件(release_policy.json)──────────┤
│ latest / minimum_supported / sunset / message   │  能力:远程宣布哪些版本还受支持
├ 3. 版本门禁(引擎内)───────────────────────────┤
│ ok → notice → required → expired(停开新单)     │  能力:过期版本无法开始新生成
└─────────────────────────────────────────────────┘
```

原则:**已生成的内容、素材库、查看与导出,任何情况下都不受限**。门禁只拦
「开新单/重跑/重做」这一族动作;续跑、单章重写、补导 Word 永远放行——
用户已经开始的活,永远允许收尾。这既是对用户的尊重,也避免"锁死数据"式的公关灾难。

## 1. 自动更新通道

- 桌面壳集成 `tauri-plugin-updater`,更新清单与更新包全部经 **minisign 私钥签名**,
  公钥固化在 `tauri.conf.json`。清单被篡改、下载被劫持都会校验失败。
- 端点(按序尝试):
  1. `https://bid-dog.vercel.app/updater/{{target}}-{{arch}}.json`(自有域名,国内可达)
  2. `https://github.com/shandianT/bid-dog/releases/latest/download/latest.json`(CI 自动产出)
- 前端:健康检查发现新版 → 侧栏「有新版 vX → 立即更新」;点击即
  `install_app_update`(下载→安装→自动重启);自动通道失败自动退回打开下载页。

### 密钥与 CI

- 私钥文件(bid-dog-updater.key)与公钥由本次交付一并提供。**私钥绝不入库**;
  在 GitHub 仓库 Settings → Secrets 配置:
  - `TAURI_SIGNING_PRIVATE_KEY` = 私钥文件全文
  - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` = 空字符串(生成时未设口令;想加口令就重新生成)
- 想自己换钥:`npx tauri signer generate -w bid-dog-updater.key`,把新公钥写入
  `tauri.conf.json` 的 `plugins.updater.pubkey`。**注意:换钥后旧安装包无法自动更
  新到新签名的版本**(校验不过),须在首个公开版本前定钥。
- CI 行为:配置了私钥 → 产出 `*.app.tar.gz(+.sig)`、`*-setup.exe.sig` 与
  `latest.json`,随 Release 附带;未配置 → 自动关闭更新产物,安装包构建不受影响。

### 每次发版清单

1. 升版本号(engine/前端钉版/tauri/包清单/CI,`tests/test_version.py` 会核对)。
2. 前移 `BUILD_SUNSET`(engine_v1.py,建议=发布日+90 天)。
3. 合入 main 触发 CI → 草稿 Release 含安装包 + 更新包 + `latest.json`。
4. 发布 Release;把 `latest.json` 同步到 `site/updater/`(可选,启用国内直连通道)。
5. 更新 `site/release_policy.json` 的 `latest`。

## 2. 发布策略文件

`https://bid-dog.vercel.app/release_policy.json`,引擎每 6 小时拉取并**本地缓存**
(断网按最后一次已知策略执行,不奖励也不惩罚离线)。字段:

| 字段 | 含义 |
|---|---|
| `latest` | 最新版本号,驱动「有新版」提示与自动更新 |
| `minimum_supported` | 最低支持版本;低于它 → `required`(限期内强提示) |
| `sunset` | `YYYY-MM-DD`;过期后低于最低支持版 → `expired`(停开新单) |
| `message` | 覆盖默认提示文案(如"本版本存在废标判定缺陷,请务必升级") |

留空 = 不启用强制。想催全量升级:把 `minimum_supported` 设为当前版,给 2-4 周
`sunset` 缓冲,`message` 写清原因。

## 3. 版本门禁与「旧版白嫖」

诚实的技术判断:**本地软件无法绝对阻止旧版本运行**(断网+改时钟总能绕)。
治理靠三件事叠加,让"守着旧版"失去意义:

1. **构建级落日**:每个安装包出厂自带 `BUILD_SUNSET`(约 90 天)。到期且长期
   联不上策略文件 → 停开新单。正常联网用户完全无感(策略文件会把在支持期的
   版本"续期");想白嫖必须永久断网——而断网就用不了大模型,产品本身失效。
2. **策略级落日**:收费开始时,把免费内测版全部划到 `minimum_supported` 之下,
   给缓冲期,到期停开新单。
3. **价值上移(商业化后)**:内置模型额度(relay)、技能包/评分规则库更新、
   模板库都走服务端按授权下发——旧版拿不到持续更新的"内容",只剩一个越来越
   过时的壳。这是比任何锁更有效的机制。

运维逃生门:`BIDDOG_NO_SUNSET=1` 环境变量一键解除门禁(现场救急/内部调试)。

## 与未来 license 的衔接

门禁的判定函数(`version_gate`)就是将来 entitlement 检查的挂载点:激活后服务端
签发短期授权票据(离线宽限 14–30 天),`expired` 的语义从"版本过期"扩展为
"授权过期"。生成入口的拦截、横幅与「立即更新/续费」动作复用同一套管线,
不需要再改一次架构。
